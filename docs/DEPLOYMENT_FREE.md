# Free-Tier Remote Deployment Guide

Target architecture: **Render (free web service) + Supabase (PostgreSQL) + Cloudflare R2 (document storage) + GitHub (source)**, single instance. This document prepares that deployment — it does not perform it. No cloud account, project, bucket, API token, or DNS record was created by this task; every step below marked "(not performed)" is left for you to execute when you're ready.

## Architecture

```
                    ┌─────────────────────┐
   GitHub  ───push──▶   Render (free)      │──── HTTPS ────▶  (future) frontend
  (source)           │  web service         │
                    │  - NestJS API        │
                    │  - in-process job    │
                    │    poller+scheduler  │
                    └──────────┬───────────┘
                               │
                 ┌─────────────┼─────────────┐
                 ▼                           ▼
       Supabase PostgreSQL          Cloudflare R2
       (pooled + direct URLs)       (document storage,
                                     S3-compatible)
```

Single instance, by construction (Render's free plan has no horizontal-scaling option) — this matches the current architecture's constraints exactly: the in-process job poller/scheduler and rate-limiter both hold in-memory/single-process state (`docs/production/SECURITY_BASELINE.md`), so this deployment target requires no changes to accommodate that.

## Render setup (not performed by this task)

1. Push this repository to a GitHub repo (see "GitHub setup" below).
2. In the Render dashboard: New → Blueprint → connect the GitHub repo → Render reads `render.yaml` from the repo root.
3. Render prompts for every `sync: false` variable in `render.yaml` (`DATABASE_URL`, `DIRECT_URL`, `BOOTSTRAP_ADMIN_PASSWORD`, `CORS_ALLOWED_ORIGINS`, R2 credentials, email placeholders) — fill these in with real values at that point, not before.
4. `generateValue: true` variables (`AUTH_JWT_SECRET`, `AUTH_MFA_ENCRYPTION_KEY`, `DOCUMENT_SIGNING_SECRET`, `ESIGN_WEBHOOK_SECRET`) are generated by Render automatically. **Verify `AUTH_MFA_ENCRYPTION_KEY` ends up as exactly 64 hex characters** — Render's generator produces a generic random string, and `MfaEncryption`'s constructor requires exactly 32 raw bytes hex-encoded; regenerate manually with `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` if the auto-generated value doesn't satisfy that.
5. Confirm the service plan is `free`, `healthCheckPath` is `/health`, and `runtime: docker` (uses this repo's `Dockerfile` directly — no separate buildpack config needed).

## Supabase setup (not performed by this task)

See `docs/DEPLOYMENT_ENV.md` "DATABASE" for the exact connection-string fields to copy. Summary:

1. Create a Supabase project (free tier).
2. Project Settings → Database → copy the **Transaction pooler** connection string → Render's `DATABASE_URL`.
3. Copy the **Direct connection** string → Render's `DIRECT_URL`.
4. No manual schema setup needed — the migration step (below) creates every table from this project's own migration history.

## Cloudflare R2 setup (not performed by this task)

1. Cloudflare dashboard → R2 → Create bucket (free tier: 10GB storage, generous free egress).
2. R2 → Manage API Tokens → Create API Token, scoped to that bucket, with Object Read & Write permission.
3. Record: Account ID, Access Key ID, Secret Access Key, bucket name → Render's `R2_ACCOUNT_ID`/`R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY`/`R2_BUCKET`.
4. Set Render's `STORAGE_PROVIDER=r2` (already the `render.yaml` default).

**This project's `R2StorageProvider` has been validated for real** against MinIO (a local S3-API-compatible emulator — see "R2 local validation" below) — the exact same code that will run against your real R2 bucket has already round-tripped real objects, computed correct byte counts, and passed the full upload→scan→download→version→IDOR flow through the actual `DocumentsService`. Only the endpoint/credentials differ between MinIO and real R2.

## GitHub setup

1. This repository currently has **no `.git` directory at all** (confirmed at every phase of this project) — `git init` and a first commit are prerequisites this task does not perform (it makes no destructive assumption about what should or shouldn't be tracked, and creating the initial commit is a decision for you, not this task).
2. Once initialized: create a GitHub repo, push, connect it to Render's Blueprint (above) for `autoDeploy: commit` to take effect.
3. `.github/workflows/ci.yml` (authored in Phase 14) is ready to run the moment this repo has a GitHub remote — install → lint → typecheck → dependency-audit → migrate deploy (against an ephemeral CI Postgres) → unit → e2e → build → Docker-image-build → deployment gate.

## Deployment order

1. Push to GitHub (once initialized) → Render Blueprint picks it up, or trigger manually.
2. Render builds the Docker image (`Dockerfile`, verified in this task — see "Local production validation" below).
3. **Before the first real traffic**: run `prisma migrate deploy` against `DIRECT_URL` as an explicit, separate step (e.g. Render's one-off "Shell" against the deployed service, or a local machine with `DIRECT_URL` pointed at Supabase) — never auto-run on container start (`docs/production/PRODUCTION_RUNBOOK.md` "migration policy").
4. Run the seed script once (`BOOTSTRAP_ADMIN_PASSWORD` must already be set in Render's env vars): `NODE_ENV=production BOOTSTRAP_ADMIN_PASSWORD=... npx prisma db seed --schema=database/schema.prisma` against `DIRECT_URL`. This creates the role/permission catalogue and exactly one `admin` user — **no demo/fixture users are created in production** (verified in Phase 14 against an isolated scratch database).
5. Render starts the container (`node apps/api/dist/main.js`, the same verified entrypoint from Phase 14/this task).
6. Verify `GET /health` and `GET /health/ready` on the real Render URL.
7. Run the smoke test checklist (`docs/production/GO_LIVE_CHECKLIST.md`'s smoke-test section, or the abbreviated one in `docs/FREE_DEPLOY_CHECKLIST.md`) using a controlled test account — log in as `admin`, exercise a couple of RBAC/document/portal paths, log out.

## Migration procedure

Identical to `docs/production/PRODUCTION_RUNBOOK.md` §3 — `prisma migrate deploy` only, run against `DIRECT_URL` (Supabase's non-pooled connection; the migration engine needs it for DDL). Never `migrate reset`, never `db push`, never run against `DATABASE_URL` directly if it's the pooled connection (some DDL isn't supported through a pooler).

## Health check

`GET /health` (liveness, no dependency check) and `GET /health/ready` (readiness, real database connectivity via Prisma) — both `@Public()` and exempt from rate limiting. `render.yaml`'s `healthCheckPath: /health` is what Render's own platform uses to gate traffic to the instance.

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| App refuses to boot, error mentions `assertProductionConfigSafe` | A required secret is missing or still a placeholder, `STORAGE_PROVIDER` is `local`, or `CORS_ALLOWED_ORIGINS` contains `*` | Read the exact error message — it lists every problem, not just the first. Fix the named env var in Render's dashboard and redeploy. |
| `AUTH_MFA_ENCRYPTION_KEY must be a 32-byte (64 hex character) key` | Render's `generateValue: true` produced a string of the wrong length/format | Regenerate manually: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`, set it explicitly. |
| `R2StorageProvider is selected (STORAGE_PROVIDER=r2) but missing required configuration` | One of `R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY`/`R2_BUCKET`, or both `R2_ENDPOINT`/`R2_ACCOUNT_ID`, is unset | Fill in the missing variable(s) in Render's dashboard. |
| `/health/ready` returns 503 | Database unreachable — check `DATABASE_URL` is the pooled Supabase string and the Supabase project isn't paused (free-tier Supabase projects pause after a week of inactivity) | Verify the connection string; unpause the Supabase project from its dashboard if needed. |
| Documents uploaded before a deploy are missing after redeploying | `STORAGE_PROVIDER` was `local` (or unset) at some point, and Render's ephemeral filesystem lost them on restart | This is exactly the failure mode `assertProductionConfigSafe()` is designed to prevent — confirm `STORAGE_PROVIDER=r2` is actually set (the check only fires at `NODE_ENV=production` boot time, so a misconfigured deploy that somehow bypassed it would need investigating). |
| Scheduled reminders/jobs seem to run late | Render free-tier spin-down (see "free-tier limitations" below) | Expected free-tier behavior, not a bug — accept it, or upgrade off the free plan if timely scheduling matters. |
| CI workflow doesn't run | No GitHub remote connected yet | See "GitHub setup" above — `.github/workflows/ci.yml` only executes once a real remote exists. |

## Free-tier limitations (be honest about these — do not pretend they don't exist)

- **Render free web services spin down after ~15 minutes of inactivity** and cold-start (10s-60s+) on the next request. The in-process job poller/scheduler is not running while spun down — a reminder sweep or scheduled job due during that window fires late, on the next request that wakes the instance up, not at its originally-due time.
- **Render free tier is single-instance only** — no horizontal scaling, which conveniently matches this project's current single-instance-scoped state (rate-limiter, job poller) without needing any change, but also means no redundancy/failover.
- **Supabase free-tier projects pause after a week of inactivity** and need manual un-pausing from the dashboard (or a request that wakes them, depending on Supabase's current free-tier behavior) — worth a periodic keep-alive if the demo needs to stay always-reachable.
- **No real email provider is connected** — `EMAIL_PROVIDER=log` remains the only implemented option; password-reset/notification "emails" are only ever logged, never actually delivered, on this free-tier target as configured here.
- **No metrics/alerting infrastructure** — unchanged from `docs/phase-status/PHASE_14.md`'s OBSERVABILITY section; Render's own dashboard provides basic request/deploy logs, nothing more.
- **Cloudflare R2's free tier** (10GB storage, no egress fees for R2-to-internet in most cases at time of writing) is generous for a demo but is still a quota — monitor usage if uploads are heavy.
