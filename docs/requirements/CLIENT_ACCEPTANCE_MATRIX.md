## POST-ROUND-2 CORRECTION (2026-08-25)

**Round 2's own `Student.school` finding (GAP-022 / REQ-STUDENT-007, "genuinely absent, not even a nullable column") was itself an audit error, not a code defect.** A follow-up read of `database/schema.prisma` for a general sheet04 conformance check found that Round 2's search only checked `model Student` for a `school` column and never checked `model AcademicRecord` — which does have one, and more strictly enforced than the fields Round 2 did credit (`grade`, `gpa`):

- `AcademicRecord.school String` — **not nullable** at the DB level (unlike `grade`/`gpa`, which are nullable by design).
- `CreateAcademicRecordDto.school` — `@IsString() @MinLength(1)`, no `@IsOptional()`: required on every create call.
- `academic-record-dialog.tsx` — a required input field in the actual form.
- Indirectly guaranteed present by `AssessmentsService.assertStudentProfileComplete`'s existing gate: it requires an `AcademicRecord` with both `grade` and `gpa` set before Assessment approval, and no such record can exist without `school` (the DTO rejects it).

The Excel's "Trường/Lớp" (sheet04 row5) is stored per-academic-period (`AcademicRecord`, alongside `grade`/`gpa`) rather than as a single fixed value on `Student` — a structural difference from sheet17's Data Dictionary literal table placement, same normalization pattern already accepted for `grade`/`gpa` themselves, not a missing field. REQ-STUDENT-002 and REQ-STUDENT-007 below are corrected accordingly (MISSING → IMPLEMENTED); GAP-022 in `CLIENT_REQUIREMENTS_GAPS.md` is marked RESOLVED (audit correction, not a code change) and the HIGH-severity tally in `CLIENT_ACCEPTANCE_REPORT.md`/`CLIENT_ACCEPTANCE_REAUDIT_ROUND2.md` is reduced by one accordingly. A new, unrelated, low-severity finding surfaced during this same check: `Activity` (Leadership/Community activities) has no `award` field, unlike `Competition`/`ResearchProject` — see new row REQ-STUDENT-008 and GAP-026.

## CLOSURE/LIQUIDATION REMEDIATION APPLIED (2026-08-26)

The client made three binding decisions resolving GAP-007/REQ-CASE-014's "two independent
closure mechanisms" finding (see the row below and `CLIENT_CLARIFICATION_SIGNOFF.md`
DEC-06/07/08), and asked for the corresponding implementation. Full design record:
`docs/requirements/CLOSURE_LIQUIDATION_DESIGN.md`; architecture decision: `docs/DECISIONS.md`
DEC-13.

1. **DEC-06 (closure owner)** — unified into ONE workflow. HCTH (`ADMIN_FINANCE`) is the
   standard executor of Hoàn tất/Đóng hồ sơ/Thanh lý; EXECUTIVE_DIRECTOR/DEPARTMENT_MANAGER
   may exercise an audited exception (`overrideReason` required, distinct audit event); the
   CONSULTANT case-owner may only request closure (advisory, non-blocking). The old
   Contract-level and Case-level paths are both retired — `PATCH /cases/:id/close` deleted,
   `PATCH /contracts/:id/status` now rejects COMPLETED/LIQUIDATED once a Case is linked
   (`409 USE_UNIFIED_CLOSURE_WORKFLOW`).
2. **DEC-07 (mandatory preconditions)** — a single server-side checklist (`GET
   /cases/:id/closure`) now covers all 6 items: công nợ, công việc còn mở, visa (the only
   item that may be NOT_APPLICABLE), xác nhận nhập học, checklist trước khi bay, and —
   previously checked by neither old mechanism — **bàn giao tài liệu** (document handover,
   a new `ClosureHandoverRecord`, never auto-inferred as not-applicable).
3. **DEC-08 (two-party liquidation)** — the old free-text `Contract.closureReason`
   liquidation note is replaced by a structured, authenticated two-party confirmation
   (`LiquidationConfirmation`): the company side (HCTH/override) and the student/parent side
   (via the Portal) each confirm independently, immutable once both are set.
